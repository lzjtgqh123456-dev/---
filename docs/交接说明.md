## 踩过的坑（写代码时注意）
1. **bash heredoc 在 Windows 下约 200 行会截断** → 长文件用 `py /d/ai/writefile.py start|append <path>` 分段写
2. **`\n` 在多字符串拼接里会被烧成真实换行** → 用多个独立 `Text` 或 `System.lineSeparator()`，不要写 `\n`
3. **`var x by remember` 必须同时导入 `getValue` 和 `setValue`**，漏一个会引发一片误导性报错
4. **`mutableStateOf` 要单独导入**
5. **Kotlin 不允许在嵌套局部函数里给 `by` 委托的局部变量赋值** → 保存逻辑内联进 onClick
6. **MSYS 会吃掉参数里的 `;`**（如 sdkmanager 的 `platforms;android-35`）→ 用 Python subprocess 传参
7. **`fallbackToDestructiveMigration()` 会清空用户数据** → 已移除，新加表必须写 Migration
8. **Room 对预置库做严格 schema 校验** → 内置词典不用 Room，走原生 SQLite（`DictStore`）
9. **ADB 装机需手机端确认**；中文文件名 push 会被截断，用 ASCII 名
10. UI 自动化在 vivo 上不稳定 → 优先用**仪器化测试直调数据层**验证（现已有 43 个设备测试）
11. **vivo 装机安全拦截**：`adb install` 会弹「安全守护提示」，需勾选「已了解应用的风险检测结果」+ 点「继续安装」；不点会一直挂着。可用后台 install + `input tap` 自动确认（坐标 [630,2302] 与 [630,2474]）
12. `TransferTest` 用共享 App DB，重复跑会因"已存在"而失败（不是回归）。⚠️ 不要用 `pm clear` 清库（会连用户数据一起清）——改用一次性测试数据或接受该用例失败
13. **vivo 文件选择器**：不要点每行的「打开」（会跳去 WPS/vivo office 打开文件）；要**先点文件行选中，再点右下角「完成」**，文件才会回给 App（选择器底部有「请选择1项文件」+「完成」）
14. **不要覆盖正在运行的 `.bat`**！cmd 边读边执行，改写会让偏移错乱、循环直接退出（踩过：覆盖 run_translate.bat 后循环停了）。要改先停循环，或用外部守护脚本收尾。
15. 仪器化测试在设备内存紧张时（`top` 显示 swap 爆满、load 十几）会从几秒变成几分钟，别误判成代码慢

### 对齐结论 / 已知差异（重要，别当 bug 查）
1. **`rel_b` 少 2 个空格**：根因是 det 缩放用 Android `Bitmap.createScaledBitmap`（Skia 双线性）而 PC 端用 `cv2.resize`（定点），
   亚像素差异让二值化后某个框左下角差 1 px（实测 `y=361` vs `362`）→ 裁剪宽 472 vs 471 → rec 输入不同 → 该行空格被吞。
   **字符级完全一致**，仅空格；已实测确认设备端解码出的图片像素与 PC **逐字节相同**（checksum 一致），所以不是色彩管理/解码问题。
2. **conf 公式**：用 PaddleOCR 的 `mean(被保留字符 max-prob)`（不是 RapidOCR 的 `mean(conf+[1e-50])`，后者会让 13 字行显示 0.9249 而不是 0.9961）。
3. **参数取值以 `tools/ocr_ref/SPEC.md` 为准**，不要照抄 RapidOCR 1.2.3 的 config（736/'min'、box .5、unclip 1.6、膨胀），
   那套在 rel_b 上会切成 5 框；本实现用 960/'max'、thresh .3、box .6、unclip 1.5、**不膨胀**、`int(round(t/32))*32` 用**五成双**。
4. **App 相对 SPEC 的唯一有意偏差**：保留了 RapidOCR 的 `text_score=0.5` 行过滤（低分行会把噪声带进后续翻译）。参考图上 6 行分数 0.93~0.998，不受影响。

### 踩坑（本批新增）
1. **JNI `n_batch=512` 的坑（已在 Kotlin 侧绕开）**：`llama_jni.cpp` 用 `llama_batch_get_one(tokens, nTokens)` 一次解码整个 prompt，
   而 context 的 `n_batch=512` —— **prompt 超过 512 token 时 `llama_decode` 直接失败并返回空串，不报错**。
   整页 OCR 文本很容易超（实测 64 行英文直接返回空）。现在 `TranslateViewModel` 按行分段（每段 ≤300 字符）逐段翻译后拼接，
   并在按钮下方显示「正在翻译第 i/N 段…」。**根治要在 JNI 里把 prompt 按 n_batch 分批 decode**（第二批可以考虑）。
2. **vivo 会冻结后台应用**：仪器化测试跑长任务时，应用一旦不在前台，测试线程和协程都会卡死（CPU 0%、心跳文件停更）。
   跑长测试前先 `am start` 把 MainActivity 拉到前台，并 `svc power stayon true`。
3. **bash heredoc 里的 `\n` 会被烧成真实换行**（本批踩到 2 次，写 Kotlin 字符串/字符字面量时用 `System.lineSeparator()` 或 `'\n'.code.toChar()`）。
4. **大图先降到长边 2048 再 OCR**（`SOURCE_MAX_SIDE`），否则 12 MP 原图 getPixels 就要 ~48 MB；EXIF 方向必须转正，否则竖拍照片必错。
5. 相册选图用 `ActivityResultContracts.PickVisualMedia`（无需存储权限）；vivo 的相册选择器**单击缩略图即选中返回**。

## 第十轮：俄文识别修复（用户反馈「西里尔字母错误率极高」）2026-09-19

### 根因（已量化）
第一批只接了**中英 rec 模型**——它词表里根本没有西里尔字母（GT 里 79.7% 的字符结构上不可能输出），
所以俄文只会被"转写成拉丁同形字"。真机截图实测（同一张图、同一套 det）：

| 模型 | 真实手机截图 CER | 合成印刷体 23 行 CER / 行全对 | 手写行级 CER |
|---|---|---|---|
| 中英 ch_v4（旧） | **66% ~ 85%** | 69~70% / 4% | 93% |
| 俄文 v3（我第一版接的） | 41% ~ 56% | 25~26% / 9% | 94% |
| **俄文 v5（现在用的）** | **0.7% ~ 2.0%** | **2.2~2.4% / 83%** | 35% |
| 手写专用 CRNN rukopys | 4% ~ 23% | 15% / 26% | **23.7%** |

数据由 `pc-ref` / `model-scout` 两套独立实现互证（详见 `docs/OCR模型源.md`、`tools/ocr_ref/out/ru_bench_report.md`）。

### 本次改动
1. **det 换 PP-OCRv5 det**（4,826,518 B）：印刷体与 v4 打平，但手写行检出 3/8 → **7/8**（v4 会整行漏检）。
2. **俄文 rec 换 PP-OCRv5 西里尔**（8,048,799 B）+ 配套 850 行词表（2,781 B，852 = 850+blank+空格）。
   两个公开转换版（PaddlePaddle 官方 `5371ee1d…` / ModelScope-RapidOCR `90f761b4…`）**数值等价**，App 里做主源+备源，各自登记大小/SHA。
3. **按行语言路由**（`OcrEngine.recognize` 的 AUTO）：先用前 1~2 行判默认模型；逐行若分数 <0.75 或结果空，就换另一个模型取更好的；
   另一个模型读出汉字时优先它（俄文词表没有汉字）。修掉"中俄混排把汉字整段丢掉"的结构性问题。
4. **模型与词表配套的运行期断言**（加载期 `classes == 词表行数 + 1`，见 `outputClasses()`）：
   不配套时 CTC 会静默输出噪声（实测踩过：165 类模型配 6623 行中英词表），现在直接判加载失败并提示重下。
5. `SOURCE_MAX_SIDE` 2048 → 3200：别把手机截图/照片里的小字先压糊。

## 第十二轮：AI 聊天加附件 + 搜索"部分引擎报错"降噪（用户反馈）2026-09-19

### 1) AI 聊天支持各种附件
**入口**：提问框下方「📎 添加附件」（多选，单个 ≤25MB）；选中后显示成可删除的 chip，随问题一起发出去。

| 附件类型 | 处理方式 |
|---|---|
| 图片（jpg/png/webp/heic…） | 长边压到 ≤1280 再转 base64，按 **OpenAI 视觉消息**（`content[].type=image_url` + data URI）发送。⚠️ 需要**模型支持视觉**（gpt-4o / qwen-vl / gemini 等）；纯文本模型会返回报错，界面原样显示 |
| 文本（txt/md/csv/json/xml/log/代码…） | 按 UTF-8 读正文（>20000 字截断），拼进提问：`【附件：name】正文` |
| Word / Excel（.docx/.xlsx） | 用 zip+xml 抽 `word/document.xml` / `xl/sharedStrings.xml` 的文字（不引第三方库） |
| 其它类型 | 只把**文件名 + 大小**告诉模型（note），不假装能读内容 |
| PDF | **暂不支持解析**（没引 PDF 库），按"其它类型"处理 |

- 只加附件不写字也能发（会自动问一句"请阅读这些附件，告诉我重点内容。"）。
- 附件在发送前才读入内存（避免大图常驻）；`file://` 这类查不到 DISPLAY_NAME/MIME 的 Uri 会用路径文件名 + 扩展名兜底（实测踩到：否则会被当成"未知类型"直接丢弃内容）。
- **设备测试** `AiAttachmentTest`（2 个用例）：
  1. 解析正确（文本→正文、图片→base64+jpeg、未知类型→note）
  2. **端到端**：附件里写"项目代号：北极星-7788"，只问"项目代号是什么？" → AI 答 **`北极星-7788`**（证明附件真的进了请求，不是只挂在界面上）

### 2) "部分引擎报错"降噪（老弹红卡）
**原因**：8 个引擎里有几个（Google/Bing/Brave/Serper）在国内网络根本连不上；原实现只要**任一**引擎失败就弹一张红色「部分引擎失败」卡，每次搜索都出现。
**改法**：
- **有结果时**：不再弹红卡，只在列表底部给一行灰色小字「ℹ️ 另有 N 个引擎没返回结果（查看原因）」，点开才显示具体错误；
- **全挂时**（`results` 为空）：保留红色卡片，但文案改成「所有引擎都没返回结果」并附一句建议
  「国内网络下 Google / Bing / Brave 等通常连不上；可以到设置里只留『免费』的 DuckDuckGo 与维基百科」；
- `SearchRepository` 超时从 连 12s/读 20s 收紧到 **连 6s/读 10s**（被墙的引擎更快失败，不再拖着整个搜索卡住）。

## 第十四轮：AI 联网搜索结论 + 预设可不选（用户反馈）2026-09-19

### 1) 「AI 的联网搜索」实测结论（**重要，别再折腾参数**）
用户配置 `BaseURL=https://api.deepseek.com`、`模型=deepseek-flash`（**官方最新模型，且支持视觉**）。
用设备测试 `AiSearchProbeTest` 把常见"服务端联网"参数逐个塞进请求体实测：

| 附加参数 | 结果 |
|---|---|
| `{"web_search":true}` | HTTP 200，但**被静默忽略**（问"今天有什么国际新闻"→ 回答"无联网"） |
| `{"enable_search":true}` | 同上，200 但无联网 |
| `{"search":true}` | 同上，200 但无联网 |
| `{"plugins":[{"id":"web"}]}` | 同上，200 但无联网 |
| `{"tools":[{"type":"web_search"}]}` | **HTTP 422**：`unknown variant 'web_search', expected 'function'` |
| `{"tools":[{"type":"web_search","web_search":{"enable":true}}]}` | 同上 422 |

⇒ **DeepSeek 官方 API 不提供联网搜索**（联网只在他们自家的 App/网页版里）；API 的 `tools` 只接受 `type:"function"`，即只能自己实现 function calling（需要自建搜索后端）。
⇒ 所以在 App 里让 AI"联网"，**唯一可行的是 App 侧检索增强**：就是「联网搜索」开关 ——
   开开后先用 DuckDuckGo + 维基百科检索，把结果整理成参考资料塞进提问（AI 回答时会标注来源）。
⇒ 已把「联网搜索」开关**恢复**（`ENABLE_WEB_SEARCH = true`），并新增「附加请求参数（JSON）」+ 常用写法一键填入，
   留给真正支持服务端检索的服务商（如 OpenRouter 的 `plugins/web`、智谱的 `web_search` 工具等）——
   填错/不被支持会直接在「测试 API 响应」里报出来。

### 2) 预设可以不选
- 默认变成**不选任何预设**（`NetViewModel.NO_PRESET = 0`），提问时用内置的通用助手提示词；
- 提问区预设行最前面加了「**不用预设**」chip；**再点一下已选中的预设也能取消**；
- 删掉当前选中的预设时回落到"不用预设"（以前会强行落到第 1 个内置预设）。

### 3) 顺带更正
`deepseek-flash` **支持视觉**（图片附件可直接发），之前文档里"deepseek-flash 是纯文本模型"的说法作废；
`deepseek-v4-flash-vision-exp` 是上一代视觉模型。官方现役：`deepseek-flash` / `deepseek-v4-pro` 等。

## 第十六轮：删掉搜索里的汇率 + 免 Key 网页搜索（用户提议无头浏览器）2026-09-19

### 1) 搜索里的"汇率"删掉了
`SearchEngine.EXCHANGE` 整个移除（枚举/默认启用/`isUsable`/分发分支/`exchangeAsResults` 全清）。
**汇率 tab 照旧**，"美元 人民币 / 100 USD to CNY" 的快捷跳转走 `ExchangeRepository.parseQuery`，跟搜索引擎无关，不受影响。

### 2) 免 Key 网页搜索：**不需要无头浏览器**，HTTP + 解析 HTML 就够了
用户问"能不能用无头浏览器访问 Google/Bing 抓摘要实现免费"。实测结论：

| 站点 | 实测（curl + 浏览器 UA） | 能用？ |
|---|---|---|
| `www.bing.com/search?q=` | 200 / ~100KB，`<li class="b_algo">` × 10，`<h2><a>` 结构稳定 | ✅ **可用**（英文/俄文查询结果相关；**中文查询会返回不相关条目**） |
| `cn.bing.com/search` | 301 跳转 | 用 www 即可 |
| `html.duckduckgo.com/html/?q=` | 200，但内容是 **"Select all squares containing a duck" 人机验证** | ❌ |
| `www.baidu.com/s?wd=` | 302 → 1.4KB 验证页 | ❌ |
| `api.duckduckgo.com`（原有） | 200，只有摘要，无网页结果 | ✅（保留） |

**结论**：抓取类"免费网页搜索"能做，但**各家都有反爬**：Bing 可用（英文/俄文靠谱，中文不稳），
百度/DDG 直接人机验证。**无头浏览器帮不上**——Google 需要 JS+Cookie 且照样弹同意页/CAPTCHA，
还要背着 WebView 的启动开销与耗电，比 HTTP 抓取更慢更脆，且违反对方 ToS。所以：
- **新增免 Key 引擎「必应网页搜索」**（`SearchRepository.bingHtml()`，jsoup 1.18.3 解析 `.b_algo`），默认启用；
- **百度已放弃**（实测被人机验证拦），代码未留；
- 保留 DuckDuckGo 摘要 + 维基百科；
- 想要稳定高质量的网页搜索，仍是填 Serper/Brave/Google CSE 的 Key（设置页「高级」里）。

### 3) 关于"免费"的现实建议
- 日常中文搜索：用「必应网页搜索」碰运气 + 维基百科；结果不理想时换 Serper（serper.dev 注册送免费额度，国内可直连）。
- 服务器/自建：SearXNG 实例最稳（设置页「高级」里可填自己的实例地址）。
- App 不会再"无脑报错"：抓取失败只进「另有 N 个引擎没返回结果（查看原因）」折叠行。
